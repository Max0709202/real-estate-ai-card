The AI chat "マンション名検索" flow lives in `backend/includes/chat-public-data-helper.php` (search/normalize/generate) and is invoked from `backend/api/chat/send.php`. Frontend renders `field:'mansion_lookup'` candidates as clickable bubble buttons in `assets/js/chat-widget.js` (`appendBubbleCandidateReplies`). DB-disambiguation buttons carry `value:'mansion_id:<id>'` → resolved by `chatMansionDbDirectAnswerById`. 表記ブレ (Ⅱ⇔2, ヶ⇔ケ, 全半角) is handled by `chatMansionNormalizeText`, which MUST stay in sync with `mansionNormalizeText` in `backend/scripts/import_mansion_buildings.php` (populates name_norm/search_norm).

**Why:** Customer repeatedly reported マンション名 lookups failing. Requirements 1-6 (normalize → RAG → LLM-format DB-only facts → disambiguate with clickable candidates → ID lookup → safe "not found" reply) are all already implemented in current code.

**How to apply:** Fixes applied 2026-07-16:
1. `chatMansionDbDirectAnswer` location-qualifier bug — selecting/typing `パレステージ江北２（東京都足立区）` made `$exactRows` empty yet the old `else` ran `$rows = $exactRows`, wiping recalled rows → "見つかりませんでした". Now only overrides `$rows` when `$exactRows` is non-empty; otherwise keeps recalled rows for confidence+location filtering.
2. Sibling candidate buttons — `chatMansionSiblingCandidates($db,$row)` (prefix match on `name_norm` with trailing 番号/館 stripped) returns the same-name family; `chatMansionBuildAnswerFromRow` now appends them as clickable `field:'mansion_lookup'` buttons (value `mansion_id:<id>`) on every direct answer, so the user can switch buildings. Chosen via AskUserQuestion "Answer + sibling buttons".

**ARCHITECTURAL HAZARD (most important):** The マンション gate in `send.php` sits IN FRONT of everything and can veto it. Two interception paths: (a) the preflight `chatMansionDbDirectAnswer()` runs on every non-land message and is NOT gated by `$isMansionLookupIntent` — if it returns an answer, `handled=true` and BOTH `processChatIntakeMessage()` and `getBotReplyWithOpenAI()` are skipped; (b) `$isUnresolvedMansionLookup` replaces the AI answer with a hard-coded 「該当するマンションが見つかりませんでした」. Everything below the gate is starvable: ヒアリング/intake, the SMS-auth trigger (lives inside intake), 進捗, attachments/画像物件特定, ローン文脈, 条件整理注入, RAG, 公的データ(相場・駅乗降客数・人口), and all general Q&A. Safe (bypass the gate): `channel:'contact'`, GPS/geo branch, land_hazard & mansion_id buttons, CRM sync.

**Do NOT use a カタカナ run to detect a building name.** 不動産用語 is overwhelmingly カタカナ — フラット35/インスペクション/サブリース/レインズ/バリアフリー/ZEH all match, and 17/17 tested terms got hijacked into 「見つかりませんでした」. A denylist cannot fix this. Trustworthy signals only: explicit marker (マンション名は○○), quoted 「○○」, or a bare proper noun with **≥2 tokens** (single-token bare カタカナ = 用語, never a building). The principled fix is an LLM intent classifier — `chatPublicDataLlmRouter()` (chat-public-data-helper.php:2868) is the working in-repo pattern (cheap model, temp=0, JSON out, 8s timeout, graceful fallback).

**Intent classifier (added 2026-07-22):** `chatClassifyMessageIntent()` in `openai-chat-helper.php` (deliberately placed there, not in chat-public-data-helper.php, because send.php requires that file directly). Cheap model via `chatOpenAIModelIntent()` / `OPENAI_MODEL_INTENT` (defaults to light), temp=0, JSON out, 8s timeout, purpose `intent_router`. Returns intent ∈ mansion|general|out_of_scope|unclear, or `unknown` on any failure → send.php falls back to the old regex routing. In send.php: `general`/`out_of_scope` set `$skipMansionDbLookup` so BOTH `chatMansionDbDirectAnswer()` calls are skipped; `out_of_scope` answers the fixed 「不動産に関するご相談を中心に…」 line but ONLY as an `elseif` AFTER `$intake['handled']`, so ヒアリング/SMS認証 keep priority; `unclear` asks the customer to clarify, but only after the DB lookup misses. The hard 「該当するマンションが見つかりませんでした」 now fires only when intent==='mansion'. The classifier is skipped for mansion_id buttons, attachments, and 土地/ハザード照会.

**out_of_scope regression + fix (2026-07-28):** After deploy, 「定休日は？」 was classified `out_of_scope` and answered the fixed rejection line, so the agent's registered RAG (定休日/営業時間, see [[agent-rag-retrieval]]) stopped being answered — the out_of_scope branch bypasses `getBotReplyWithOpenAI()` where 担当者追加RAG is injected. Two-layer fix: (1) classifier prompt in `chatClassifyMessageIntent()` now explicitly maps agent/company operational questions (営業時間・定休日・休業・連絡先・対応エリア・アクセス・会社概要・自己紹介・あなたは誰/何ができる・挨拶) to `general`, since the AI is the agent's 分身 and may hold registered info. (2) SAFETY NET in send.php: `chatAgentHasMatchingCustomRag($db,$cardId,$message)` (new, in chat-rag-helper.php) — term-based LIKE against `agent_custom_rag_items` with NO recent-RAG fallback (unlike getAgentCustomContextForChat, whose fallback loads recent rows even on no match, so it can't be used to decide "did it match"). If a registered RAG matches, `out_of_scope` is flipped to `general` before routing, so anything the agent registered is never blocked. Guard both with function_exists (transitive include).

**out_of_scope 誤拒否 + 会話の断絶 fix (2026-07-30):** 「ワイド団信とは何ですか？」が out_of_scope 判定で固定拒否文になった（軽量モデルが知らない専門用語を対象外に倒す）。また AI 自身が「CIC・JICC・KSCそれぞれの取り方を整理します」と提案した直後の「CICを教えて」が `unclear` 判定で「ご質問の意図を確認させてください」と聞き返された。分類器プロンプト（住宅ローン専門用語の明示列挙／out_of_scope は確信できる場合だけ／迷ったら general／直前AI発言の続きは general）に加え、send.php に決定的セーフティネット2本を追加: `chatMessageLooksRealEstateRelated($message)` (関連語の巨大 alternation。**逆向きには使わない**＝語が無いことを対象外の根拠にしない) と `chatMessageContinuesPreviousReply($message, $conversationHistory)` (直近 bot/agent 発言に、最新発言中の英数2字以上／カナ漢字3字以上のトークンが含まれるか＋最新発言40字以内)。両方 openai-chat-helper.php（send.php が直接 require するファイル）に置き、function_exists ガード付き。out_of_scope は general へ倒すが、**unclear は general に倒してはいけない** — general は `$skipMansionDbLookup=true` になり全国マンションDB先行照会が消えるため。unclear は「聞き返し分岐に `&& !$isFollowUpContinuation` を足す」だけにして DB 先行照会を残す。誤って general へ倒しても本文プロンプト（openai-chat-helper.php の「不動産と無関係な雑談には無理に不動産回答を返さない」ルール）が丁寧に受け流すので、拒否より安全側。

**通学区域（学区）が答えられなかった件 + fix (2026-07-31):** 「エルザタワー55の通学区域を教えて」が①マンション未識別②学区未表示になった。原因は2つ。(1) `chatMessageAsksLandInfo()` に学区語が無く土地照会と見なされないため、マンションDB先行照会が生メッセージで走り、検索語が「エルザタワー55の通学区域」になって0件→固定文「該当するマンションが見つかりませんでした」で確定していた（`chatResolveMansionAddress()` のノイズ語除去にも学区語が無かった）。(2) reinfolib カタログの XKT004 keywords が `小学校区|学区`、XKT005 が `中学校区` だけで、「通学区域」ではどちらも（XKT005 は「学区」でも）マッチしなかった。修正：`chatMessageAsksLandInfo()` を `chatMessageAsksLandHazardInfo()` + 新設 `chatMessageAsksSchoolDistrict()` の OR に分解し、ノイズ語除去に学区語を追加。`chatMansionLandQueryAddress()` はテーマ別にクエリを作り分け（学区なら「{住所} の通学区域（学区）を教えてください」／`topic_label` を返し send.php の先頭見出しに使う）。**クエリ文言に「小学校」「中学校」を入れてはいけない** — 学校位置レイヤ XKT006 まで一致し、最寄り校を学区校と取り違えるため「通学区域（学区）」表記に固定している。XKT004/XKT005 には `coverage=>true` を付け、ポリゴン0件を「指定されていません／区域外」ではなく「データなし（自治体未整備・未公開）」と言わせる（`chatReinfoZoneStatusItem`）。なお複合質問（学区＋ハザード）ではプロバイダ5件上限（レジストリ順スライス）で XKT005 が落ちることがある。

**公的データ質問が out_of_scope で拒否された件 + fix (2026-08-17):** 「新中野駅の乗降客数は？」が `out_of_scope` 判定になり固定文「不動産に関するご相談を中心に…」で返された。乗降客数(XKT015)・人口(e-Stat)などのプロバイダは実装済みで、`chatPublicDataShouldRun()`（駅|乗降|人口 等を含む）も true を返すのに、send.php の out_of_scope 分岐が `getBotReplyWithOpenAI()` 手前で打ち切るため公的データ照会に到達していなかった。既存セーフティネット `chatMessageLooksRealEstateRelated()` には駅・乗降・人口・地価などの公的データ語が入っていない（不動産取引語彙のみ）ため素通りしていた。修正：(1) `chatMessageAsksPublicOpenData()` を openai-chat-helper.php に新設（`chatPublicDataShouldRun()` に委譲＝公的データを取りに行く質問＝必ず答える質問、という単一基準。function_exists 未定義時は自己完結キーワードにフォールバック）。(2) send.php にセーフティネット4：out_of_scope かつ公的データ質問なら general へ倒す。(3) 同じ `$isPublicDataQuestion` を `unclear` の聞き返し分岐の除外条件にも追加（聞き返さずAI回答へ渡す。unclear は general に倒さない＝DB先行照会を残す方針は維持）。(4) 分類器プロンプトに「乗降客数・人口・地価・都市計画・ハザード・学区・周辺施設は不動産情報ライブラリ/e-Stat で回答できるので必ず general」を明記。

**`send.php` fragility:** it catches only `Exception`, so an undefined function (an `Error` in PHP 7+) is NOT caught → every message 500s → "all features broken". It also does NOT `require` chat-public-data-helper.php (transitive include), so a partial deploy of one file kills the chat. Guard new cross-file calls with `function_exists()` and deploy both files together.

**Debugging lesson:** The カーサ新宿 "not found" was NOT a code bug — the live chat was posting to a **different backend** than the migrated staging one (widget `apiBase = data-api-base || location.origin + '/backend/api/chat'`). Diagnostic tool `backend/scripts/diagnose_mansion_lookup.php` (read-only; loads the same includes as send.php) reproduces the full pipeline on any server and prints where it breaks. Also note: opcache on the web tier can serve stale code even after deploy (`validate_timestamps` may be off) — CLI always runs fresh, so CLI-works/web-fails ⇒ suspect backend origin or opcache. Delete the two temp scripts (`diagnose_mansion_lookup.php`, `opcache_reset_web.php`) once done. Verify the deployed branch matches `develop` before assuming a code bug.

**住所抽出の致命的バグ + 学区の言い回し + 価格APIの市区町村突合 fix (2026-08-30):** 「東京都中央区新川1丁目14-9の小学校はどこ」「同住所近辺の取引価格・成約価格・地価情報」がどちらも「確認できませんでした」になった。原因は3つ、いずれも独立。
(1) **`chatExtractAddressFromMessage()` が「1丁目14-9」形式を取りこぼす。** `$banchi` の丁目分岐は `N丁目(N番地?)?(N号)?` だけで、ハイフン番地（1丁目14-9）も番号のみ（1丁目14）も無かった。「1丁目」までしか食えず末尾の boundary `(?![0-9…])` が次の数字で失敗 → regex が右へずれ、`ja{1,24}`＝「丁目」＋`14-9` で **「丁目14-9」** を住所として返していた。GSI ジオコーディングが必ず失敗 → `chatReinfoResolveLatLon()` が null → **その住所のXKT***系GIS照会が全滅**（学区・ハザード・用途地域・地価ポイント全部）。丁目つき住所の大半（東京23区の表記は「N丁目N-N」が普通）が該当する広範囲な障害だった。丁目分岐に「N丁目N-N（-N）」「N丁目N」を追加。**順序が重要**：番地・号形式を先に置かないと「1丁目14番9号」が「1丁目14」で切れる。
(2) **`chatMessageAsksSchoolDistrict()` が「学区」語しか見ていない。** お客様は「どの小学校になる？」「小学校はどこ」と聞く。学区照会と認識されず、ルーターも XKT006（学校の位置）しか選ばず、システムプロンプトの【学区】ルールが「小学校区を確認できませんでした」を出していた。小学校|中学校 への言及は原則 学区照会とし、周辺|近く|近い|近隣|最寄|付近 を伴う場合だけ施設照会（XKT006）に倒す。あわせて `chatPublicDataRoute()` に決定的インジェクションを追加：学区照会なら XKT004/XKT005 を先頭に必ず入れ、XKT006 は外す（最寄り校と学区校の取り違え防止）。
(3) **`chatReinfoCityCode()` の突合が片方向。** `chatPublicExtractArea()` の市区町村regexは貪欲で「東京都中央区新川1丁目…」から **「東京都中央区」** を返す（都道府県込み）。API側の名称は「中央区」なので `mb_strpos($name,$cityName)` は必ず false → **都道府県名を書いた住所では XIT001（取引価格・成約価格）が常に0件**。双方向 contains ＋ 一致名称が最長の行を採用、に変更（「中区」⊂「横浜市中区」対策）。
また `chatResolveMansionAddress()` は、テーマ語除去後に残る疑問形の残骸（「シティハイツ東京日本橋はどの になる？」）を丸ごと建物名として検索していたため0件になっていた。`はどの|はどこ|になりますか|になります|になる|どの|どこ|ですか…` の二段目クリーンアップを追加。**テーマ語リストは3箇所（`chatMessagePointPublicDataTopics()` / `chatResolveMansionAddress()` のノイズ除去 / カタログ keywords）で同期が必要。**
プロバイダ上限は一律5件 → 種類別（区域＝ポリゴン8件／周辺施設＝ポイント4件）に変更。「洪水・高潮・津波・土砂・液状化・盛土を全部」のような複合質問で層が黙って落ちるのを解消（最悪タイル数 8×1+4×9=44 で従来 5×9=45 と同等）。
検証用CLI: `backend/scripts/verify_reinfolib_apis.php --address=... / --mansion=...`（全35API・読み取り専用・チャットと同じ取得関数）。
